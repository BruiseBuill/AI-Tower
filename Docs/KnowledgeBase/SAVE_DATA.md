# 存档设计

## 已确认需求

- 游戏为单机，存档保存在本地。
- 项目包含关卡进度和成长，因此二者需要进入存档。
- 当前工程已有 Easy Save 3 和 `BF.MomentoManager` 雏形。

## 默认边界

在用户进一步确认前，存档至少预留以下分区：

- `schemaVersion`：存档结构版本。
- 玩家设置：音量及以后确认的本地选项。
- 关卡进度：已解锁、已完成及关卡成绩字段。
- 成长进度：货币、解锁项、升级等级或等价内容。
- 教学状态：已完成的教学步骤，避免重复强制教学。
- 当前内容版本或其他迁移辅助信息。

字段只是设计边界，具体类型和含义要等玩法确认后定义。

## 实现原则

- 在 `BaseFramework` 的存档入口之上定义本游戏的具体存档模型，不创建第二套无关入口。
- 不直接保存场景对象、MonoBehaviour 或 ScriptableObject 实例；保存稳定 ID 和纯数据。
- 每次结构变更递增 `schemaVersion`，提供从旧版本到新版本的迁移路径。
- 读取失败时保留原文件并给出可诊断日志，不直接覆盖损坏存档。
- 自动保存使用临时文件/备份或 Easy Save 3 的等价安全机制，降低写入中断风险。
- 存档不存在时创建明确的默认数据；默认值集中定义。
- Android 生命周期中至少考虑暂停、失焦和正常退出时保存，具体时机需结合玩法决定。
- 不在每帧或高频事件中写磁盘。

## 待确认

- 单一自动存档还是多个存档槽。
- 是否允许清除进度或重新开始。
- 关卡成绩记录哪些指标，例如星级、耗时、剩余资源或最佳解法。
- 局中退出是否保存战斗现场，还是只保存局外进度。
- 成长是否可以重置或洗点。

在这些问题确认前，可以建立接口和版本机制，但不应固定最终字段。
