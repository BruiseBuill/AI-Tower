# 玩法框架

## 已确认的宏观结构

玩家处于进攻方，在俯视角地图中通过轻量点击、滑动和 UI 操作组织进攻，突破由
防御塔和地形构成的关卡。内容由简单教学逐步扩展至复杂塔型和复杂地形，并包含一套
成长体系。

## 默认设计方向（尚非最终规则）

在用户确认具体规则前，开发应围绕以下最小闭环保持可扩展性：

1. 进入关卡并观察地图、进攻起点、目标和敌方防御。
2. 玩家消耗某种局内资源选择并部署进攻单位或进攻方案。
3. 单位沿规则允许的路径推进，防御塔自动选择目标并攻击。
4. 玩家通过有限且轻量的操作调整后续部署或触发能力。
5. 达成目标后胜利；进攻资源耗尽或满足失败条件后失败。
6. 结算关卡结果，写入进度与成长数据，再进入下一关或重试。

该闭环只用于约束系统边界，资源形式、部署方式、路径规则和胜负条件仍需确认。

## 关卡递进建议

- 教学阶段：一次只引入一种操作或一种规则。
- 基础阶段：组合少量单位、基础塔和简单岔路。
- 中期阶段：加入塔之间的协同、射程覆盖、特殊地块或多路径压力。
- 后期阶段：组合复杂地形、复杂塔型、资源限制与多个战术目标。

关卡不能只靠提高生命和伤害制造难度。优先通过新关系、新限制和不同解法增加深度。

## 数据驱动边界

以下内容应设计为可配置数据，不直接写死在场景脚本中：

- 进攻单位属性、能力、占位与正式资源 ID。
- 防御塔属性、索敌规则、攻击方式和资源 ID。
- 关卡地图引用、路径/节点、可部署区域、初始资源和胜负条件。
- 关卡解锁、奖励与成长配置。
- 全局数值曲线及中文显示文本。

优先使用 ScriptableObject 定义静态配置。运行时状态和存档数据使用独立的普通 C#
数据结构，避免直接序列化场景对象或 ScriptableObject 实例。

## 移动端交互约束

- 鼠标左键与单指触摸必须走同一套语义层：按下、移动、释放、点击和拖动。
- UI 触摸不得穿透至战场操作。
- 不依赖鼠标右键、滚轮、键盘或悬停提示完成必要操作。
- 拖动阈值应按屏幕 DPI 或合理的参考分辨率适配，不能只使用固定像素假设。
- 危险或不可逆操作应有明确确认或易于撤销。
- 双击和长按不是首选主操作，除非用户确认它们确实改善体验。

## 首个垂直切片建议

- 一张可完整通关和失败的地图。
- 一种进攻单位。
- 一种防御塔。
- 一种部署资源。
- 最小点击或拖动部署操作。
- 基础战斗、目标、暂停、胜负结算和重试。
- 保存关卡完成状态与必要设置。

垂直切片规则应在 `OPEN_QUESTIONS.md` 的最高优先问题确认后再正式实现。
